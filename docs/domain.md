# 业务规则 (Domain Rules)

本文件定义不可变的业务逻辑。AI 在生成相关代码时必须严格遵守以下规则（编号可通过测试用例验证）。

## 用户与认证 (AUTH)
- **AUTH-01**：用户密码必须使用 `nuxt-auth-utils` 提供的 `hashPassword` 进行哈希，禁止明文存储。
- **AUTH-02**：未登录用户访问需要鉴权的接口，必须返回 `401 Unauthorized`。
- **AUTH-03**：已登录但无权限（非 ADMIN）访问管理后台接口，必须返回 `403 Forbidden`。
- **AUTH-04**：登录凭证为邮箱，`email` 必须唯一；`phone` 可选，填写后也必须唯一；`nickname` 仅用于展示，可空且不唯一；密码长度不得少于 8 位；注册成功后直接建立会话（不需要二次登录）。
- **AUTH-05**：会话有效期为 7 天，过期后必须重新登录。
- **AUTH-06**：会话密钥使用 `NUXT_APP_SECRET`（nuxt-auth-utils 0.6 起已弃用 `NUXT_SESSION_PASSWORD`），长度不得少于 32 字符，禁止提交到仓库。
- **AUTH-07**：个人资料允许修改 `nickname`、`phone` 与 `email`；修改 `email` 必须额外校验当前密码（见 AUTH-11），修改 `phone` 必须校验当前密码并完成短信验证（见 AUTH-16）；头像本期不做（DISH-07 的上传只服务菜品图，不扩展到头像）。
- **AUTH-08**：`nickname` 可空、可重复，填写时长度 2–20 字；`phone` 可空，填写后必须唯一，空串统一存 `null`。唯一性校验**不得过滤 `deletedAt`**，与注册保持一致（见 DATA-03）。
- **AUTH-09**：修改密码必须验证当前密码，新密码长度不得少于 8 位，且只存 `hashPassword` 结果；禁止任何接口返回 `passwordHash`。
- **AUTH-10**：资料修改成功后必须用最新 `email` / `nickname` 重写会话（`setUserSession`），前端随后 `session.fetch()`；否则「我的」页头部会继续显示旧昵称。
- **AUTH-11**：邮箱修改必须满足：① 请求里带 `currentPassword` 并通过校验，否则返回 400（会话被盗时不能被改走登录凭证）；② 新邮箱先 `trim` 并转小写，格式与注册一致；③ 全局唯一校验**不得过滤 `deletedAt`**（DATA-03，已注销账号仍占用原邮箱）；④ 被占用返回 409；⑤ 修改分两步（见 AUTH-15）：请求只写待确认字段并发确认邮件，确认前 `email` 不变、原邮箱继续可登录；确认成功后用新邮箱重写当前会话（AUTH-10），且不递增 `sessionVersion`（其他设备仍凭同一账号 id 有效，只是会话里的邮箱展示值滞后到下次登录）。
- **AUTH-12**：会话失效与账号注销。
  - `User.sessionVersion` 默认 `0`，登录/注册写入会话时一并写入当前版本；受保护接口统一用 `requireActiveUser(event)` 校验「账号未软删除 + 会话版本与数据库一致」，不一致返回 401（提示重新登录）。
  - 修改密码与账号注销必须自增 `sessionVersion`，使其他设备的下一次请求立即 401（AUTH-05 的 7 天有效期不再是唯一失效途径）；修改密码后当前设备需用新版本重写会话，避免把自己踢下线。
  - 游客可访问的接口（随机推荐 `/api/dishes/random`、AI 推荐 `/api/recommend`）统一用 `getOptionalActiveUser(event)`：未登录或会话已失效一律按游客处理，禁止沿用失效会话里的 `userId` 读取该账号的偏好/历史或扣账号配额。
  - 账号注销为 `DELETE /api/me`：软删除（写 `deletedAt`）+ 自增 `sessionVersion` + `clearUserSession`；收藏与历史按 DATA-02 保留；注销后邮箱/手机号不可再注册（DATA-03），前端二次确认文案必须写明这一点。
- **AUTH-13**：登录与注册必须限流：进程内滑动窗口按「IP + 账号」计数，1 分钟内失败达到 5 次后第 6 次起返回 429 并附中文提示；成功登录清空该账号的失败计数；注册按 IP 限流。限流是**单实例内存实现**，多实例部署时需替换为 Redis 等共享存储（代码注释必须写明该前提）。
- **AUTH-14**：找回密码（P2-04）。
  - 申请 `POST /api/auth/forgot-password`：无论邮箱是否存在都返回同一成功响应，禁止暴露账号是否存在；同一 IP+邮箱 1 分钟内最多申请 5 次，超出返回 429。
  - token 使用 32 字节加密随机数（base64url），数据库只存 SHA-256 哈希与 15 分钟过期时间（`User.resetTokenHash` / `User.resetTokenExpiresAt`）；每次申请覆盖旧 token；重置成功后清空，**不可复用**；过期视为无效。
  - 重置 `POST /api/auth/reset-password`：校验哈希与过期时间，失败统一返回 400「重置链接已失效，请重新申请」；成功后更新密码哈希、清空 token、自增 `sessionVersion`（AUTH-12）并清当前会话，使所有旧会话立即失效。
  - 邮件通道使用 Resend HTTP API（原生 fetch，不新增依赖），配置 `NUXT_RESEND_API_KEY` / `NUXT_MAIL_FROM` / `NUXT_APP_URL`；未配置时开发环境打印日志并在响应里返回 `devResetUrl`（仅 `import.meta.dev`），生产环境返回 503「邮件服务未配置」。发送失败必须清空 token 并提示稍后重试，禁止假装发送成功。
- **AUTH-15**：邮箱换绑邮件验证（P2-05）。
  - 申请 `PATCH /api/me/profile`：昵称立即生效；手机号变化按 AUTH-16 走短信验证；邮箱变化时**不直接改 `email`**，只写 `User.pendingEmail` / `pendingEmailTokenHash` / `pendingEmailExpiresAt`，并向新邮箱发送确认链接（30 分钟有效、单次有效，每次申请覆盖旧 token）。
  - token 规则与 AUTH-14 一致：32 字节加密随机数、数据库只存 SHA-256 哈希、链接根地址取 `NUXT_APP_URL`；同一用户 10 分钟内最多申请 5 次，超出返回 429。
  - **先发信、后写库**：发信失败或生产环境未配置邮件服务时返回 503，且不得留下「永远收不到确认链接」的待确认记录；未配置 Resend 时开发环境返回 `devConfirmUrl`（仅 `import.meta.dev`），生产环境禁止把确认链接回传给调用方。
  - 确认 `POST /api/auth/confirm-email`：不要求登录（用户可能换设备点链接），校验哈希与过期时间，失败统一返回 400「确认链接已失效，请重新申请换绑」；确认时再次校验邮箱唯一性（含软删除占用，DATA-03），被占用返回 409。
  - 确认成功：写入 `email`、清空 pending 三个字段；若当前浏览器登录的正是该用户，用新邮箱重写会话但**不递增 `sessionVersion`**（与 AUTH-11 ⑤ 一致）。确认前原邮箱始终可登录。
- **AUTH-16**：手机号换绑短信验证（用户口径的 P2-06 需求）。
  - 手机号与邮箱一样可用于登录，属于登录凭证，因此换绑同样分两步：`PATCH /api/me/profile` 校验当前密码与全局唯一（含软删除占用，DATA-03）后，只写 `User.pendingPhone` / `pendingPhoneCodeHash` / `pendingPhoneExpiresAt` / `pendingPhoneAttempts`，并向新号码发送 6 位验证码；确认前 `phone` 不变、原手机号仍可登录。
  - 验证码为 6 位数字、5 分钟有效、单次有效；数据库只存 SHA-256 哈希；同一验证码最多输错 5 次，达到上限即作废；每次重新申请覆盖旧验证码并重置计数。
  - 发送前按用户限流：与邮箱换绑共用 `assertContactChangeAllowed`（10 分钟 5 次，超出 429），一次请求同时改邮箱和手机号只计一次。
  - 确认 `POST /api/me/phone/confirm` 必须登录，验证码与当前账号绑定；校验过期、错误次数与唯一性后原子写入 `phone` 并清空 pending 字段；失败统一返回 400「验证码已失效，请重新获取」/「验证码不正确」，号码被占用返回 409。
  - 清空手机号不需要短信验证，直接生效并清空 pending 记录（不会新增登录入口，无需证明号码归属）。
  - 短信通道当前未接入供应商：开发环境在响应里返回 `devCode`（仅 `import.meta.dev`）便于联调；生产环境返回 503「短信服务未配置」，禁止把验证码回传给调用方。
- **AUTH-17**：账号禁用（P2-11）。
  - `User.disabledAt` 非空表示账号被管理员禁用。被禁用账号**登录一律返回 403**「账号已被禁用，请联系管理员」，即使密码正确也不得签发会话；受保护接口返回 403，公开接口按游客处理（`getOptionalActiveUser` 返回 null）。
  - 禁用属于运营手段，**不是注销**：不写 `deletedAt`，收藏、就餐历史、反馈等数据全部保留；启用后原账号可直接恢复登录，无需重新注册（区别于 AUTH-12 的账号注销）。
  - 禁用时必须自增 `sessionVersion`（AUTH-12），让已签发会话的下一次请求立即 401，不能等 7 天过期。
  - 管理员不能禁用自己、不能修改自己的角色、不能重置自己的密码，服务端返回 400：避免把自己锁在后台外；管理员改密请走个人资料页（AUTH-09）。

## 管理后台 (ADMIN)
- **ADMIN-01**：后台用户管理（`/api/admin/users`）只允许 ADMIN（每个 handler 第一行 `requireAdmin`）。列表支持按邮箱 / 手机号 / 昵称模糊搜索、角色筛选、状态筛选（`ACTIVE` / `DISABLED`）与分页；软删除账号不出现在列表，状态由 `disabledAt` 是否为空推导。
- **ADMIN-02**：禁用 / 启用 / 角色变更 / 重置密码 / 新增、编辑、删除菜品与分类都必须写入 `AdminAuditLog`（`adminId` / `action` / `targetType` / `targetId` / `detail` / `createdAt`）。审计与业务更新必须在**同一事务**内提交，避免「数据改了但没记录」；`targetType` 只允许 `USER` / `DISH` / `CATEGORY`，`targetId` 只做逻辑引用（目标物理删除后审计仍保留）；`detail` 只记录变更后的值（如新角色、菜名），**禁止记录密码明文或哈希**。
- **ADMIN-03**：角色变更与被禁用都会自增目标账号的 `sessionVersion`：目标账号下一次请求 401，需重新登录才能拿到新角色。管理员重置密码只改 `passwordHash` 并让旧会话失效，不得回传新密码。
- **ADMIN-04**：审计记录只读：后台提供 `GET /api/admin/audit-logs`（`targetType` 筛选 + 分页，时间倒序），**不提供任何修改或删除审计的接口**；查询响应必须带操作人邮箱，便于追责。
- **ADMIN-05**：数据看板口径固定：总量取当前全量（排除软删除），趋势 / 热门菜 / 零结果搜索 / AI 指标取「最近 7 或 30 天」；`days` 只接受 7 / 30。趋势必须补齐没有数据的日期，热门菜按 `DiningHistory` 次数统计（不依赖前端埋点），AI 指标来自 `AiCallLog` 落库数据。
- **ADMIN-06**：菜品质量巡检只筛「资料不完整」的菜：`missing=image`（`imageUrl` 为 `null` 或空串）、`missing=allergens`、`missing=ingredients`。**不提供「无分类」筛选**：DISH-01 要求菜品必须归属分类，缺少分类属于脏数据，应通过迁移修正而不是做成筛选。
- **ADMIN-07**：批量与导入导出：单次批量最多 200 条、单次 CSV 导入最多 500 行；批量操作与导入都必须逐条写审计（`CREATE_DISH` / `UPDATE_DISH`）。CSV 导入必须支持 `dryRun` 预校验，失败行返回 Excel 行号与原因；**非法行不落库**，合法行在一个事务内写入。CSV 由服务端自实现解析（`server/utils/csv.ts`），不引入第三方库。

## 菜品与推荐 (DISH)
- **DISH-01**：菜品必须归属于唯一一个 `Category`。
- **DISH-02**：随机推荐接口必须保证真正的随机性（数据库层面使用 `RANDOM()`），且每次只返回 1 条。
  - 叠加偏好/地域/天气后属于**加权随机**，仍由数据库 `RANDOM()` 产生随机性（`ORDER BY -LN(RANDOM()) / weight`，指数竞赛采样），禁止改成应用层 `Math.random()` 加权。
- **DISH-03**：搜索接口必须支持模糊匹配（菜名包含搜索词），且不区分大小写。
  - 中文没有大小写概念，PostgreSQL 的 `ILIKE` 即可满足，不必为此引入全文索引。
  - 一期**不做**拼音首字母搜索（如 `csf` → 吃啥饭），禁止为此引入分词或拼音库。
- **DISH-04**：「换一个」必须由前端回传 `excludeIds`（本次已展示过的菜品 id），服务端在候选池内排除它们，保证候选池耗尽前不重复。
  - 候选池为空时必须降级为全量随机，禁止直接返回「没有可推荐的菜」。
- **DISH-05**：推荐默认排除当前用户近 `HISTORY_DAYS`（默认 3 天）内 `DiningHistory` 记录过的菜品；显式传 `includeRecent=true` 时不排除。游客无历史，不受此条约束。
  - 去重窗口由用户在「我的」页设置：`historyDays=0`（不限，允许推荐最近吃过的）/ `3`（默认）/ `7`（更久不重样）。`historyDays` 优先于 `includeRecent`：传了 `historyDays` 就按它算天数，`0` 等同于不按历史去重。
  - 这是本地展示偏好（useState + localStorage），不写入 `UserPreference`、不跨设备同步。
- **DISH-06**：`Dish.mealType` 取值只能是 `BREAKFAST` / `LUNCH` / `DINNER` / `ANY` 之一，用于餐别筛选。
- **DISH-07**：菜品图片支持后台上传，也可以继续填外链。上传只允许 ADMIN，格式限 JPG / PNG / WebP（按文件头魔数判断，不接受 SVG），单张 ≤5MB；文件落在 `UPLOAD_DIR`（默认 `.data/uploads/dishes`，Docker 部署挂持久化卷），数据库只存站内相对路径 `/uploads/dishes/<uuid>.<ext>`。文件名由服务端生成，禁止使用客户端文件名。换图时若旧图已无其它菜品引用则删除旧文件；外链不受本站管理，不做删除。
- **DISH-08**：`RANDOM()` 是 PostgreSQL 的全表扫描。当前数据量（千级以内）无感知，但必须在接口注释中写明这一前提，避免后期被误判为性能缺陷。

## 收藏 (FAVORITE)
- **FAV-01**：同一用户对同一菜品只能有一条收藏记录。
- **FAV-02**：用户取消收藏时，若记录不存在，应返回成功（幂等性），而不是报错。
- **FAV-03**：`(userId, dishId)` 必须在数据库层建立唯一索引（Prisma 的 `@@unique`），不能只靠应用层判断，否则并发收藏会产生重复记录。

## 就餐历史 (HISTORY)
- **HIST-01**：一条记录表示「某用户某天吃了某道菜」，字段为 `userId` / `dishId` / `eatenOn`（只存日期，不含时间）。
- **HIST-02**：同一用户、同一天、同一道菜只保留一条记录，由 `@@unique([userId, dishId, eatenOn])` 保证。
- **HIST-03**：历史只由用户主动点击「今天就吃它」写入，单纯浏览或刷新推荐结果不得写入历史，否则去重逻辑会把推荐池吃空。
- **HIST-04**：就餐历史可撤销（P2-07）。
  - `DELETE /api/history/:id` 只能删除本人记录；`eatenOn` 必须落在「今天 + 前 6 天」共 7 个自然日内，超出返回 403「只能撤销最近 7 天的就餐记录」。
  - 记录不存在或属于他人统一返回 404，禁止用 403/410 暴露「该 id 存在但不属于你」。
  - 撤销是硬删除（历史是日志，不适用 DATA-02 软删除）；撤销后该菜品立即回到推荐候选池，前端列表同步移除并递减总数。
  - 前端入口为历史页左滑「撤销」，必须二次确认（撤销会影响推荐去重与统计），禁止静默删除。

## 一餐与推荐单元 (MEAL)
- **MEAL-01**：推荐的最小单位是「一餐」，不是「一道菜」。把一串烤串、一份小菜单独当作一餐展示属于错误实现。
- **MEAL-02**：一餐只有两种形态：单品餐（一份粉/面/饭/套餐即可吃饱）与组合餐（主食 + 1~3 道菜）。
- **MEAL-03**：`Dish.servingMode` 只能是 `SINGLE`（单品即一餐）或 `DISH`（需要搭配主食的菜）。
- **MEAL-04**：组合餐必须恰好包含 1 道 `MAIN`（主菜），可选 1 道 `VEG`（素菜）和 1 道 `SOUP`（汤），菜品总数不超过 3。
- **MEAL-05**：组合餐的主食从全局主食池（米饭 / 馒头 / 面条 / 粥 / 饼）中按**主菜菜系 + 餐别**加权选取，不再固定为「米饭」；主食不是 `Dish` 记录，不参与推荐、收藏与搜索。
- **MEAL-06**：单品餐不参与组合，抽中即为完整一餐。
- **MEAL-07**：去重按菜品粒度执行：组合餐涉及的每一道菜都要计入 `excludeIds`，并遵守 DISH-05 的近 3 天规则。
- **MEAL-08**：候选池被 `excludeIds` / 近 N 天历史筛空时必须清空 `excludeIds`（历史去重保留）重新抽，禁止因此返回「没有可推荐的一餐」。
  - **例外**：忌口过敏原（PREF-02）与辣度上限（PREF-03）是硬约束，筛空后必须返回「没有符合条件的一餐」，禁止为了凑结果放宽硬约束。

## 口味偏好与推荐上下文 (PREF)
- **PREF-01**：每个用户最多一条 `UserPreference`（`userId` 唯一），字段包含喜欢菜系、不喜欢菜系、忌口过敏原、辣度上限、价格上限；未登录或未填写时使用默认值（无忌口、辣度上限 3、价格上限 3）。
- **PREF-02**：**忌口/过敏原是硬过滤**：菜品的 `allergens` 与用户忌口列表有交集时直接排除，降级重抽（MEAL-08）也不得放宽。
- **PREF-03**：**辣度上限是硬过滤**：只推荐 `spicyLevel <= 用户 spicyMax` 的菜品。
- **PREF-04**：**喜欢/不喜欢菜系是软加权**：喜欢的菜系权重 ×3、不喜欢的 ×0.2，不硬排除；因此「不喜欢烧烤」仍可能偶尔抽到烧烤，这是预期行为。
- **PREF-05**：同一个菜系不能同时出现在「喜欢」和「不喜欢」中，服务端必须拒绝（400）。
- **PREF-06**：**地域与天气只做软加权**：按用户所在省份/城市映射地域口味，按当前天气（高温 / 寒冷 / 雨雪 / 温和）调整菜系权重；两者合并倍率上限 2.5，不得变成硬筛选。
- **PREF-07**：IP 定位或天气获取失败/超时必须 **fail-open**：接口照常返回推荐结果，仅 `ambient.city` / `ambient.weather` 为空，禁止让首页报错或阻塞。
- **PREF-08**：忌口使用**受控过敏原枚举**（`Allergen`：花生 / 坚果 / 海鲜 / 鱼 / 牛肉 / 羊肉 / 猪肉 / 禽肉 / 蛋 / 乳制品 / 麸质 / 大豆 / 芝麻 / 酒精），由后台多选维护，禁止用户自由输入文本。
- **PREF-09**：定位只保留城市级信息，不落库、不回传经纬度，避免隐私问题；第三方调用结果做进程级缓存（城市 1 小时、天气 30 分钟、失败 5 分钟）。
- **PREF-10**：甜品 / 蛋糕 / 面包等烘焙类**本期不进入菜系与餐食推荐**（需求后置），后续接入时需先补充菜系与推荐单元规则。
- **PREF-11**：**「不感兴趣」是持久化反馈，7 天内硬排除**：登录用户对某道菜标记不感兴趣后，随机推荐与 AI 候选都必须排除该菜，窗口从 `DishFeedback.createdAt` 起算 7 天；`DishFeedback` 以 `(userId, dishId, action)` 唯一，重复标记只刷新时间，撤销即硬删除。游客不落库，只沿用本次会话的 `excludeIds`；排除导致候选为空时返回空态，禁止为了凑结果放宽。
- **PREF-12**：**「喜欢」是持久化反馈，7 天内软加权 ×1.5**：登录用户对某道菜点「喜欢」后，随机推荐权重与 AI 候选排序都乘以 1.5，但**不硬推**，避免推荐池被点赞菜垄断；`LIKE` 与 `DISLIKE` 对同一道菜互斥，写入一种时必须在同一事务里删除另一种，防止「既加权又排除」的不可解释状态。游客不落库，点击时提示先登录。

## AI 智能推荐 (REC)
- **REC-01**：AI 只能推荐真实候选池里的菜。候选由 `listRecommendCandidates` 生成，硬过滤规则与随机推荐完全一致（PREF-02/03：忌口过敏原、辣度上限）并默认排除近 3 天吃过的与近 7 天内标记「不感兴趣」的菜（PREF-11）；候选被硬约束筛空时返回友好提示，禁止放宽忌口为凑结果。候选清单不再整体注入 prompt，改由 `recommend_dishes` 工具按需返回（REC-10）。
- **REC-02**：菜品数据以数据库为准。模型回复末尾的 `<<DISHES:["菜名",...]>>` 标记只表示「模型的选择」，服务端按菜名匹配候选并回查数据库（未删除、已上架）组装真实 `DishDetail`，禁止把模型输出的菜品字段直接透传；标记解析失败或菜名匹配不到时按纯文本回复处理。**候选清单禁止暴露内部 id**（曾导致回复正文出现「d15 螺蛳粉」这类编号），正文若仍残留 id 必须由服务端清洗后再下发。
- **REC-03**：LLM 供应商通过环境变量 `NUXT_LLM_BASE_URL` / `NUXT_LLM_MODEL` / `NUXT_LLM_API_KEY` 配置（OpenAI 兼容 chat/completions 协议），切换供应商只改 `.env` 不改代码；任何失败（未配置 Key、鉴权失败、限流、超时、上游 5xx）都以 SSE `error` 事件收尾并附中文提示，禁止让前端崩溃或裸抛 500。
- **REC-04**：地域与天气必须写入 system prompt（城市、天气与一句口语化提示），让模型能解释「为什么现在推荐这顿」；口味偏好（喜欢/不喜欢菜系、辣度、价格）同样进 prompt，口径与 PREF-01~05 一致。
- **REC-05**：多轮对话 history 由前端随请求带回，**服务端只取最近 5 轮（10 条）**，单条限 300 字，更早的直接丢弃、不做摘要；错误气泡不进入下一轮历史。用工具参数替代隐式指代消解：模型看到历史后应把「那有没有不辣的」改写成完整 query 传给 `search_knowledge`。
- **REC-06**：模型只能基于工具返回的事实（菜名/菜系/辣度/价格/标签/食材/做法）描述菜品，禁止声称某道菜含有清单之外的菜品或食材（实测曾出现「烧烤套餐里含辣子鸡」的幻觉）；用户想吃的菜不在候选池时，必须明确告知「菜品库里暂时没有 XX」后再给最接近的替代，禁止用幻觉迎合用户。
- **REC-07**：AI 请求次数配额：登录用户默认 30 次/天（`NUXT_AI_DAILY_QUOTA_USER`），游客按 IP 默认 5 次/天（`NUXT_AI_DAILY_QUOTA_GUEST`）；在请求上游前扣减，超限直接返回 SSE `error` 事件且**不得请求上游**。次数配额仍是进程内内存计数（防刷用），多实例部署需换共享存储；成本控制见 REC-12。
- **REC-08**：**知识库检索**：菜品同步为知识片段（一菜一片，做法超 300 字单独成片）并写入 `knowledge_chunks`（pgvector `vector(1024)` + HNSW 余弦索引）。检索 topK=6、相似度阈值默认 0.35（`NUXT_RAG_THRESHOLD` 可调）；embedding 未配置或调用失败时自动降级为关键词 bigram 匹配（fail-open，禁止让问答整体不可用）。后台增删改、批量、CSV 导入后异步重建该菜片段；全量回填用 `npm run db:embed`。
- **REC-09**：**诚实拒答**：检索无命中时 `search_knowledge` 返回 `found:false`，服务端在「无任何推荐结果」时用固定文案「菜品库里暂时没有这方面的信息。」收尾，禁止把内部提示原样交给模型复述；`result` 事件通过 `grounded` / `knowledgeMiss` 透传，前端在未命中时显示「没有找到相关依据」。知识库范围仅限菜品库与 App 自身规则，库外问题（如「北京哪家店好吃」）一律不答，不联网编造。
- **REC-10**：**工具（skill.md）**定义在 `server/assets/skills/*.md`，元数据为 HTML 注释中的 JSON 块（name / description / whenToUse / parameters），正文作为工具说明注入。可用工具白名单：`get_current_time`、`get_location`、`get_weather`、`recommend_dishes`、`search_knowledge`、`record_feedback`；所有参数必须 Zod 校验，非法参数返回 `{ ok:false }` 而不是 500。模型不得通过参数构造任意查询或访问白名单外的能力。`get_location` 复用请求入口已解析的 ambient 信息（IP 城市/省份），不重复调用第三方定位；`get_weather` 返回 `mealHint`（天气餐食建议），与 system prompt 里的天气提示口径一致。
- **REC-11**：**Agent loop**：决策阶段最多 5 步（非流式、带 tools），步数用尽或额度耗尽后必须进入作答阶段；单轮 LLM 调用 ≤6 次（5 次决策 + 1 次流式作答），单次超时 30s、整轮预算 60s、单轮 token 预算 6000；同一工具同参数最多调用 2 次。决策阶段 `max_tokens` 压到 200，最终答案用流式返回以保留打字机效果。
- **REC-12**：**Token 配额**：登录用户默认 50000 tokens/天（`NUXT_AI_DAILY_TOKEN_USER`），游客按 IP 默认 20000（`NUXT_AI_DAILY_TOKEN_GUEST`，单轮约 5k，保证至少 4 轮），按 `(subjectKey, day)` 落库 `ai_usage_daily` 并用数据库原子自增；与按次数的 `consumeAiQuota` 两套口径并存，任一不满足都拒绝且不请求上游。请求前剩余 <200 直接拒绝；每次模型调用后推送 `quota` 事件；客户端中途断开时已消耗的 token 仍必须记账。优先使用上游 `usage`，缺失时按字符数 /1.5 估算。
- **REC-13**：**AI 推荐必须以「一餐」为单位**：`recommend_dishes` 按 `servingMode` / `role` 组装「主菜 + 配菜 + 汤 + 主食」，不得返回一堆同角色菜品；关键词与餐别是软筛选，筛空时退回全量并说明原因，禁止因此拒答。模型漏写 `<<DISHES>>` 标记时，服务端用工具选中的菜品兜底出卡片，保证有推荐就有卡片。

## 推荐效果埋点 (TRACK)
- **TRACK-01**：只埋真实推荐链路上的三类事件：`IMPRESSION`（推荐结果展示给用户）、`CLICK`（用户点开推荐菜品卡片）、`DINE`（用户点「就吃它」并成功记录就餐）。来源 `source` 仅允许 `RANDOM`（首页随机一餐）/ `AI`（AI 聊天推荐）。
- **TRACK-02**：前端必须**批量**上报（2s 防抖或队列满 20 条触发，单批最多 50 条），每条事件由前端生成全局唯一 `eventId`；服务端按 `eventId` 唯一键 `skipDuplicates` 去重，重复提交不得产生重复行。
- **TRACK-03**：埋点允许游客上报（`userId` 为空），登录用户写入 `userId`；只采集 `userId / dishId / type / source / eventId / createdAt`，**禁止采集 IP、设备指纹、UA 等额外个人信息**。
- **TRACK-04**：埋点是旁路能力，上报失败必须静默吞掉，**禁止影响抽签、AI 推荐、就餐记录等主流程**；服务端对不存在或已删除的 `dishId` 直接丢弃，不得因脏数据返回 500。

## 搜索 (SEARCH)
- **SEARCH-01**：最近搜索词**只存本机 localStorage**（最多 10 条，最新置顶、不区分大小写去重），不上传服务端；用户可一键清空。搜索历史属于设备级轻量偏好，不做跨设备同步。
- **SEARCH-02**：只在输入防抖（300ms）结束、真正发起搜索时记录搜索词；空词不记录，避免把输入过程中的半截词写进历史。
- **SEARCH-03**：搜索或分类筛选**无结果时必须给可点击兜底**，禁止只显示空文案：展示相近分类（优先取热门菜所属分类，不足用现有分类补齐）与热门菜（近 30 天就餐次数 Top 6，不足用最新上架菜补齐），保证用户不会停在死胡同。
- **SEARCH-04**：只有「关键词搜索且结果为 0」时才写 `SearchLog`（关键词 + 结果数），用于后台看板发现菜库缺口；正常搜索不写库。写日志失败不得影响搜索请求（异步、吞异常）。

## 数据约定 (DATA)
- **DATA-01**：`User`、`Category`、`Dish` 使用 `deletedAt` 软删除：非空即视为已删除，所有业务查询必须默认过滤 `deletedAt: null`，禁止直接物理删除。
- **DATA-02**：`Favorite` 取消收藏直接硬删除；`DishFeedback` 撤销「不感兴趣」同样硬删除；`DiningHistory`、`RecommendEvent` 作为行为日志保留，不做物理清理。
- **DATA-03**：唯一字段在软删除后仍占用原值（例如已注销账号的邮箱不能再注册）。MVP 接受该限制；若需释放，应改为原生 SQL 迁移的部分唯一索引（`WHERE deleted_at IS NULL`），禁止在应用层绕过唯一约束，**也禁止在删除时给 `email` / `phone` / `name` 拼接 `_deleted` 等后缀**——那会改写业务数据、破坏回滚，且只靠应用层自觉，无法保证一致性。
- **DATA-04**：固定枚举值（`Role` / `MealType` / `ServingMode` / `DishRole` / `Allergen` / `DishFeedbackAction` / `RecommendEventType` / `RecommendSource`）使用 Prisma enum，不建字典表；菜系由 `Category` 表承载，可动态增删。
- **DATA-05**：禁止新增 `ext Json`、`remark` 这类万能备用字段；需要时按业务新增语义明确的列并写迁移。
- **DATA-06**：索引只在查询真的用到时才加：用户端列表与随机推荐固定带 `deletedAt is null` + `isPublished`，因此保留 `dishes(isPublished, deletedAt)`；按菜统计收藏必须有 `favorites(dishId)`。模糊搜索仍走 `ILIKE`，当 `dishes` 超过 5000 行或搜索 P95 超过 300ms 时才启用 `pg_trgm` GIN，**不提前引入扩展**。

## SEO 与抓取 (SEO)
- **SEO-01**：所有页面必须通过 `usePageSeo`（`app/composables/usePageSeo.ts`）设置标题、描述与 Open Graph，禁止页面里各写一份 `useHead`；菜品详情页的标题/描述/封面图跟随菜品数据。
- **SEO-02**：`robots.txt` 与 `sitemap.xml` 由服务端路由生成（跟随部署域名），只收录公开页面与在架菜品；`/admin`、`/api`、`/me`、`/history`、`/favorites`、`/preferences`、`/chat` 必须 `Disallow`。
